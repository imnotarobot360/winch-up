# The 1 October migrations have not applied to production

**Status: production is running today's frontend against yesterday's schema.** This needs twenty
minutes in the Supabase SQL editor. Nothing is broken that this does not fix.

## How this is known, not assumed

`POST /rest/v1/rpc/<function>` with the **publishable** key is a legitimate unauthenticated way to
ask production whether a function exists: `42501` means it is there and the gate works, `PGRST202`
means there is no function with that name *and those arguments*. Measured at 19:14 UTC, 52 minutes
after the first push and 75 minutes after the first migration was committed:

| probe | answer | meaning |
|---|---|---|
| `member_profile {p_user_id}` | `42501` | exists — September's version |
| `nearby_members {p_query}` | `PGRST202` | **the new signature is absent** |
| `request_photos_for_helper {p_request_id}` | `PGRST202` | absent — from this morning's commit |
| `member_rigs`, `report_member`, `admin_suspend_member`, `admin_restore_member`, `moderation_reported_members` | `PGRST202` | all absent |

The argument matters: calling a function with the wrong parameter names returns `PGRST202` and reads
exactly like a missing migration, so each of these was probed with its real signature.

Meanwhile `https://www.winch-up.com/members` serves the new copy in its own metadata — "Everyone who
has joined. Nearest to you first." So Vercel deployed and Supabase did not. The GitHub integration
applied a migration in about ninety seconds on 30 September; it has applied none of 1 October's.

## What that actually costs, right now

- **The member directory loaded empty-handed.** The page calls `nearby_members` with `p_query`, which
  the old function has no parameter for. Fixed from the app side in `b189d1a`: on `PGRST202` it asks
  again without the argument and filters in the browser, which is what it did until today. So the
  directory works either way — but it is working on the OLD rules, which means the two consent gates
  are still in force and most members are still invisible. The owner's spec is not in effect yet.
- **Reporting a member fails** with "That did not go through." `report_member` does not exist.
- **The moderation screen's new section** shows its error line.
- **The photographs for members in the ring** are never offered: `/api/requests/[id]/photos` returns
  404 because `request_photos_for_helper` does not exist. It degrades to "no photos on this one",
  which is the designed fallback and reads as a recovery without pictures rather than as a fault.
- **Suspension does not exist**, so there is still no way to remove an abusive account — which is the
  one gap here that matters on a day when a profile is visible to everybody.

Nothing is silently wrong. Every one of these degrades to a visible absence rather than a wrong
answer, which is the only reason this is a twenty-minute job and not an incident.

## Applying them

In the Supabase SQL editor, paste these **one file at a time, in this order**. They are in
`supabase/migrations/`.

1. `20261001000500_exclude_requester.sql` — a requester is not dispatched to their own recovery
2. `20261001000600_first_ring_ten_miles.sql` — the first ring is 10 miles, per the spec
3. `20261001000700_photos_for_ring.sql` — members in the ring may see the photographs
4. `20261001001000_open_directory.sql` — suspension, and the shared listability rule
5. `20261001001100_directory_open_rpcs.sql` — the directory stops asking permission
6. `20261001001200_dispatch_respects_suspension.sql` — suspension and blocking reach the dispatcher
7. `20261001001300_profile_rigs_and_activity.sql` — rigs and community activity on a profile
8. `20261001001400_report_and_suspend_members.sql` — report a member, suspend one
9. `20261001001500_content_queue_excludes_members.sql` — a reported member is not content
10. `20261001001600_reported_members_by_member.sql` — one row per member, suspended ones kept
11. `20261001001700_report_a_member_again.sql` — somebody can be reported more than once
12. `20261001001800_community_report_conflict_target.sql` — and a post can still be reported

**The order is not optional.** 4 creates the function 5 and 6 depend on; 11 replaces the constraint
that 12 fixes the inference for. Each file is safe to run twice — they are `create or replace`,
`add column if not exists`, `create index if not exists`.

**One file per paste.** A large paste into that editor has silently truncated before, and a
half-applied function file is worse than an unapplied one.

## Then check, with one statement

Run `docs/verify-which-migrations.sql`. It is one statement returning one row per file, failures
sorted to the top, and it now covers all of the above — including the things existence checks cannot
see:

- `arg nearby_members ~ p_query` — the function has existed since September. Only the **argument**
  tells you whether today's file ran, and it is the exact thing whose absence broke the directory.
- `noref member_profile ~ profile_public` — this file's job is a REMOVAL, so "does the function
  exist" has been true for weeks and proves nothing.
- `ring10 dispatch.ring_radii_miles` — 20261001000600 changes data, not structure.
- `reportkind member` — the CHECK constraint exists either way; what matters is the value in it.

Read every row, not just the top. It sorts failures first, so the top is the bad news and the rest is
what tells you whether anything else is wrong.

## And then the integration itself

Worth finding out why it stopped, because the next migration will go the same way. From here it is
not possible to tell whether it is disconnected, pointed at another branch, or failing on a specific
statement — that needs the Supabase dashboard, which only the owner can open. The repository's
standing assumption, written in CLAUDE.md on 30 September, is that migrations apply themselves on a
push; until this is understood, treat that as something to verify after every deploy rather than
something to rely on.
