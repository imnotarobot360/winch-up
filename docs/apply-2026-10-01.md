# The 1 October migrations: applied by hand, and verified

**Status: DONE.** All thirteen were pasted into the Supabase SQL editor on 1 October and verified the
same evening. Nothing here is outstanding. Kept because the next time the integration stops this is
the procedure, and because two of the traps below are not specific to this batch.

## How it was verified

Two halves, neither of which trusts the other.

**From outside, over HTTP with the publishable key.** A function answers `42501` when it exists and
the gate works, `PGRST202` when there is no function with that name and those arguments. And --
established with controls rather than assumed -- PostgREST validates a COLUMN name *before* it checks
the table grant, so a column that does not exist answers `42703` while one that does answers `42501`.
A deliberately fake column name was used as the control each way. That settled nine functions
(`nearby_members` with `p_query`, `member_rigs`, `report_member`, `admin_suspend_member`,
`admin_restore_member`, `moderation_reported_members`, `request_photos_for_helper`, `member_profile`,
`community_report`) and four columns (`profiles.suspended_at`, `suspended_reason`, `suspended_by`,
`vehicles.show_in_community`).

**From inside, with one statement.** `docs/verify-2026-10-01.sql` covers the four kinds of thing the
HTTP probes cannot reach: anything in schema `app`, a function replaced under the same signature, an
index, and a setting's value. Eighteen rows, all `ok`.

Together those two cover every file in the batch. Before that, four of the twelve were resting on
inference, and the difference between twelve applied and eight applied plus four assumed is the whole
point of having a verifier.

## The original problem, for next time

### What the probes said at 19:14 UTC, before any of it was applied

`POST /rest/v1/rpc/<function>` with the **publishable** key is a legitimate unauthenticated way to
ask production whether a function exists: `42501` means it is there and the gate works, `PGRST202`
means there is no function with that name *and those arguments*. Measured at 19:14 UTC, 52 minutes
after the first push and 75 minutes after the first migration was committed:

| probe | answer | meaning |
|---|---|---|
| `member_profile {p_user_id}` | `42501` | exists — September's version |
| `nearby_members {p_query}` | `PGRST202` | **the new signature is absent** |
| `request_photos_for_helper {p_request_id}` | `PGRST202` | absent — from this morning's commit |
| `member_rigs`, `report_member`, `admin_suspend_member`, `admin_restore_member`, `moderation_reported_members` | `PGRST202` | all absent |

The argument matters: calling a function with the wrong parameter names returns `PGRST202` and reads
exactly like a missing migration, so each of these was probed with its real signature.

Meanwhile `https://www.winch-up.com/members` serves the new copy in its own metadata — "Everyone who
has joined. Nearest to you first." So Vercel deployed and Supabase did not. The GitHub integration
applied a migration in about ninety seconds on 30 September; it has applied none of 1 October's.

### What it cost while it lasted

- **The member directory loaded empty-handed.** The page calls `nearby_members` with `p_query`, which
  the old function has no parameter for. Fixed from the app side in `b189d1a`: on `PGRST202` it asks
  again without the argument and filters in the browser, which is what it did until today. So the
  directory works either way — but it is working on the OLD rules, which means the two consent gates
  are still in force and most members are still invisible. The owner's spec is not in effect yet.
- **Reporting a member fails** with "That did not go through." `report_member` does not exist.
- **The moderation screen's new section** shows its error line.
- **The photographs for members in the ring** are never offered: `/api/requests/[id]/photos` returns
  404 because `request_photos_for_helper` does not exist. It degrades to "no photos on this one",
  which is the designed fallback and reads as a recovery without pictures rather than as a fault.
- **Suspension does not exist**, so there is still no way to remove an abusive account — which is the
  one gap here that matters on a day when a profile is visible to everybody.

Nothing is silently wrong. Every one of these degrades to a visible absence rather than a wrong
answer, which is the only reason this is a twenty-minute job and not an incident.

## READ THIS FIRST: the order is load-bearing, and skipping file 4 breaks the directory

Observed at 19:40 UTC: `nearby_members` with `p_query` answered `42501`, and so did `member_rigs`
and `report_member` — so files 5, 7 and 8 were applied. But `profiles.suspended_at` did not exist,
which means **file 4 was not**.

That is the one combination worse than applying nothing. `nearby_members()` and `member_profile()`
from file 5, and `member_rigs()` from file 7, all call `app.member_is_listable()` — which **file 4
creates**. A plpgsql body is not checked for the functions it calls when it is created, only when it
runs. So those three functions install perfectly, report themselves as present, and then raise
`42883 undefined_function` for every signed-in member who opens the directory or any profile.

The app's `PGRST202` fallback does not cover this: that one catches "no function with those
arguments", and this is a function that exists and fails inside. The screen shows "Could not load
members".

**If you are in this state, run file 4 now.** It is additive and safe to run twice. Then carry on
with 6, then 9 through 12, then go back for 1, 2 and 3.

## File 1 is superseded by file 6, and now says so itself

`20261001000500_exclude_requester.sql` replaces `app.candidates()` **whole**, and mentions neither
suspension nor blocking. `20261001001200_dispatch_respects_suspension.sql` replaces it whole again
and adds those three conditions while keeping the self-dispatch exclusion file 1 introduced. So file
6 contains everything in file 1, and file 1 contains none of file 6.

In a clean replay the order handles it. Applying by hand does not: pasting file 1 after file 6 would
quietly put a suspended member back on the dispatch ring and let somebody be called out to a
recovery filed by a person who blocked them — with no error and nothing on any screen to show it.

File 1 now checks before it acts. If the live `app.candidates()` already mentions `suspended_at` it
prints

```
NOTICE:  skipped: app.candidates already carries 20261001001200's conditions, which include this file's
```

and does nothing. Proven in both directions: against a database that already has file 6 it skips and
all three conditions survive; against one that does not, it applies and the self-dispatch exclusion
appears. So file 1 is safe to paste at any point, and a `supabase db reset` still builds correctly
because the guard is false at that point in the order.

That pattern is worth copying. A migration that replaces a whole function is a migration that can
revert a later one, and "paste them in order" is a sentence, not a mechanism.
## What NOT to paste

Only files from `supabase/migrations/`. Two neighbours are easy to grab by mistake:

- **`supabase/tests/*_test.sql`** — pgTAP suites. They insert fake accounts into `auth.users`, they
  need the `pgtap` extension, and they are written to run against a local database. They do wrap
  themselves in `begin; … rollback;`, so one that errors part-way commits nothing — which is why
  pasting `directory_test.sql` into the production editor on 1 October did no damage. Still not a
  thing to run there.
- **`supabase/seeds/demo.sql`** — creates demo accounts with a written-down password. It refuses to
  run against production by design; do not help it.

A quick way to tell them apart: a migration never contains `select no_plan()`, `select is(`, or
`rollback;`.
## Applying them

In the Supabase SQL editor, paste these **one file at a time, in this order**. They are in
`supabase/migrations/`.

1. `20261001000500_exclude_requester.sql` — a requester is not dispatched to their own recovery
2. `20261001000600_first_ring_ten_miles.sql` — the first ring is 10 miles, per the spec
3. `20261001000700_photos_for_ring.sql` — members in the ring may see the photographs
4. `20261001001000_open_directory.sql` — suspension, and the shared listability rule
5. `20261001001100_directory_open_rpcs.sql` — the directory stops asking permission
6. `20261001001200_dispatch_respects_suspension.sql` — suspension and blocking reach the dispatcher
7. `20261001001300_profile_rigs_and_activity.sql` — rigs and community activity on a profile
8. `20261001001400_report_and_suspend_members.sql` — report a member, suspend one
9. `20261001001500_content_queue_excludes_members.sql` — a reported member is not content
10. `20261001001600_reported_members_by_member.sql` — one row per member, suspended ones kept
11. `20261001001700_report_a_member_again.sql` — somebody can be reported more than once
12. `20261001001800_community_report_conflict_target.sql` — and a post can still be reported

**The order is not optional.** 4 creates the function 5 and 6 depend on; 11 replaces the constraint
that 12 fixes the inference for. Each file is safe to run twice — they are `create or replace`,
`add column if not exists`, `create index if not exists`.

**One file per paste.** A large paste into that editor has silently truncated before, and a
half-applied function file is worse than an unapplied one.

## Then check, with one statement

Run `docs/verify-which-migrations.sql`. It is one statement returning one row per file, failures
sorted to the top, and it now covers all of the above — including the things existence checks cannot
see:

- `arg nearby_members ~ p_query` — the function has existed since September. Only the **argument**
  tells you whether today's file ran, and it is the exact thing whose absence broke the directory.
- `noref member_profile ~ profile_public` — this file's job is a REMOVAL, so "does the function
  exist" has been true for weeks and proves nothing.
- `ring10 dispatch.ring_radii_miles` — 20261001000600 changes data, not structure.
- `reportkind member` — the CHECK constraint exists either way; what matters is the value in it.

Read every row, not just the top. It sorts failures first, so the top is the bad news and the rest is
what tells you whether anything else is wrong.

## What is known about why the integration stopped

Not much, and the honest version is that it cannot be diagnosed from the repository.

**GitHub has no record of it, ever.** Checked across today's commits and a commit from 30 September,
the day it demonstrably applied a migration in ninety seconds: no commit status, no check run, no
deployment from any Supabase app. Only Vercel and this repo's own CI. So the absence of a Supabase
signal today proves nothing — there has never been one. That rules out the obvious theory (it ran and
failed loudly somewhere visible) and leaves the answer inside the Supabase dashboard, which only the
owner can open.

**A replay would be safe, and this is measured rather than assumed.** All twenty-one of 1 October's
migrations were re-run against a database that already had every one of them: zero failures, and both
verifiers still reported everything present afterwards. That matters because the hand-applied files are
almost certainly absent from `supabase_migrations.schema_migrations`, so if the integration ever wakes
up it will try to apply all of them again. It can. The files are `create or replace`,
`add column if not exists`, `create index if not exists`, `alter type ... add value if not exists`,
`drop constraint if exists` before `add constraint`, and two guarded `do $$` blocks.

### The one query that would settle it

```sql
select version, name
  from supabase_migrations.schema_migrations
 order by version desc
 limit 25;
```

If 1 October's versions are absent, the integration never recorded them and the schema and its history
have diverged — the objects exist, the ledger does not know. `supabase migration repair --status
applied <version>` is how that is reconciled, and it needs the CLI and the database password.

### Two candidates worth checking in the dashboard

1. **Is the integration still connected at all**, and to this repository and branch? Integrations →
   GitHub. The simplest explanation for "no signal anywhere, ever" is that it reports only in the
   dashboard, and the second simplest is that it is disconnected.
2. **`supabase/config.toml` declares `major_version = 15`.** If the project is on a different Postgres
   major, the shadow database the integration builds to validate migrations cannot be created, and the
   run fails before it touches anything. Worth comparing against the project's actual version.

### The alternative, which may be better than fixing it

This repository's CI already installs the Supabase CLI and runs `supabase start` for the test job. A
job that runs `supabase db push` on a merge to main would replace an integration that reports nowhere
with a step that fails loudly in a place already being watched. It needs `SUPABASE_ACCESS_TOKEN` and
the project ref as repository secrets, and it deploys schema automatically — so it is the owner's call,
not something to add unilaterally.
